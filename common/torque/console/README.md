# console

## C++ DSO v33 reader (2026-11-09)

The active C++ reconstruction now has a format-only loader in `dso.hpp` /
`dso.cpp`, separate from the parked Pascal experiment. This is the first
loader slice of [#172](https://github.com/squirelworks/graal-client-repro/issues/172).
It is not yet connected to either boot host and does not execute scripts.

Build with `make -C common/torque/console`; run the synthetic checks with
`make -C common/torque/console test`. The `torque-dso` workflow builds and
tests only this component on Linux, Windows and macOS. Linux also runs the
same cases under address/undefined-behavior sanitizers. Builds/tests run on
CI or cloud machines, not the owner's Windows capture host.

Inspect an external, owner-supplied file without executing it:

```
common/torque/console/build/dso-inspect --little-floats FILE.dso
common/torque/console/build/dso-inspect --big-floats FILE.dso
```

The caller selects float byte order explicitly: little for the documented
Linux 3.04 profile, big for the documented PPC float-table variant. Integer
fields remain little-endian. There is no plausibility-based autodetection.
The reader preserves string/float tables, decoded code words, line pairs
and identifier-use groups. It does not intern names, patch code words or
validate instruction semantics. An unused argument (identifier offset at
or past the table end; the shipped 3.04 files use both) is represented
separately from a named empty string.

### Provenance and validation policy

Implemented from the published behavior-only
[DSO v33 format description](https://github.com/squirelworks/Graal_analysis/blob/main/torque/scripting.md#file-format-version-33).
No original scripts, binaries, proprietary engine sources or recovered code
are included. `tests/dso_test.cpp` contains a hand-written 90-byte fixture:
global strings `A`/`B`, function string `F`, floats 1.0/-2.5, four code words
(including an escaped 32-bit value), one line pair, one named relocation and
one unused-argument sentinel. Expected fields are asserted directly rather
than generated by the reader or a matching encoder.

The tests also cover explicit PPC float bytes, every truncated prefix,
oversized counts, bad version, invalid/unterminated identifier references,
out-of-range relocation uses, trailing bytes, empty tables and unchanged
caller state after failure. Resource limits (16 MiB input, 1,048,576 items
per counted table), strict trailing-byte rejection and malformed-reference
rejection and a 16 MiB total copied-identifier-name budget are reproduction
hardening policies, not claims about original
error handling. Relocation targets are checked against code length; their
instruction/operand role and line-table semantics require the later VM.

## Instruction structure inspection

`dso-inspect --little-floats FILE.dso --instructions` optionally decodes
instruction boundaries and checks absolute branch, object-failure and
function-body end targets. The default invocation remains format-only.
`instructions.hpp` exposes the structural decoder without depending on a VM.
It uses the published Graal3.x opcode numbers/operand widths, including the
variable function declaration header and argument list. Undocumented2/3/72
and out-of-range opcodes fail explicitly; operand values are not opcodes.

Targets must identify an instruction or the stream-end boundary; function
body ends cannot precede their header's end. These are structural validation
policies, not proof that a branch is reachable or executable. Identifier
relocations, string/float reference types, function nesting, line-table
semantics and runtime behavior are not validated. A stream-end target may be
structurally valid even when a particular executor rejects falling off code.
The decoder limits input to1,048,576 words and leaves caller output unchanged
on failure. No original script payloads are bundled.

Independent fixtures check declaration argument widths, reserved-looking
operand values, fixed-width instruction families, truncated headers/operands,
bad targets and output atomicity. The test target also exercises the real
inspection CLI against synthetic valid/unknown-opcode DSO bytes, checking
that optional decoding succeeds or returns exactly exit1 as appropriate.

## Historical surface inventory

The inventory below describes the earlier research snapshot, not completed
implementation or universal claims about all platforms in a version family.
Current per-build contracts and unresolved loader reachability are tracked
in #151. Absence of a string alone does not prove absence of a script path.

**Stock** TGE 1.2. The script console: namespaces, packages, the native command registry, and loading plain `.cs` and compiled `.dso` v33 (Graal's opcode numbering, big-endian float tables on PPC).

What it has to do, when the hold lifts: boot the way 3.04 boots (`setModPaths`, `exec` of the shipped `main.cs` chain), and expose the stock global commands the shipped scripts call (`echo`, `exec`, `export`, `schedule`, `isObject`, the file helpers). Graal's own calls are `guigraal`, not this unit. The parked `TqCode` / `TqCompile` / `TqVM` units are an unfinished interpreter for this job. They are not wired in, and this stub does not call them.
