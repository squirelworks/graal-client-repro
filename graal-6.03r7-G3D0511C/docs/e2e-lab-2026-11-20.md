# End-to-end lab: the rebuilt 6.03r7 through the Seihai suite (2026-11-20)

Issue #373. Two rebuilt 6.03r7 clients played one session through the
Seihai listserver, a Login server and a game server, in a headless Debian
lab VM with loopback only (127.0.0.1). This note keeps the derived
results; the captures, logs and screenshots stay in the lab.

## Setup

| Piece | What |
|---|---|
| Client build | `main` at the merge of #424, `scripts/build.sh graal-6.03r7-G3D0511C`: Graal603 (start screen) and `quattro-play` |
| Art | Seihai's default art in the 6.x `levels/` layout; no original 6.03r7 data |
| Client A | Graal603 start screen on Xvfb: nick, account, server list, Connect; it hands the game to `quattro-play` |
| Client B | `quattro-play --build 6.03r7 --connect 127.0.0.1:<login port>` |
| Listserver | seihai-listserver 0.1.1 |
| Login server | the GServer-v2 fork (gs2emu 4.0.0-beta), `serverside = true`; a level NPC does `serverwarp` to the game server, so the client gets 178 |
| Game server, pass 1 | the same fork, `serverside = true`; two levels with a right-edge link; Bomb, Bow and a GS2 weapon that sets `player.chat` |
| Game server, pass 2 | the Rust seihai-gserver (a lab-tree build of the same day), world from `import-v2` of the same folder |
| Wire | a gen-5 decoding proxy in front of each server, logging both ways and able to inject a packet |

## Client findings

1. **Level links were never followed by the client.** `quattro-play` stored
   PLO 1 but never sent a warp, so on a server that leaves links to the
   client the player stopped at the edge. Fixed in #425: the walk tests one
   point, the body's centre 1.25 tiles ahead, as the 2.05 lab measured, and
   sends one LEVELWARP (0) until the server answers with 6, 14 or 15.
   Re-run with the fix (same day): on the Rust server both clients sent
   one C>S 0 per crossing, both ways (`issho_b.nw` at 2,30 and back to
   `issho_a.nw` at 61,30); the server answered with 6 and the board, no 14,
   and each client sent 46. On the fork with `serverside = false` it went
   the same way. A 5-minute soak on Rust passed (29 ping answers).
   That run found two more things, both fixed in #425: the client kept its
   old x after the warp (the server sends no position with the 6, so the
   client now puts itself at the link's arrival when the level comes), and
   the fork sent 6 twice for one crossing, which drew two 46s (a repeat of
   the same level name is now one entry).
2. **Chat and nicknames are not drawn** over players. Prop 12 goes both
   ways. 6.x draws no built-in chat in this rebuild (`player_chat` is a
   4.x/5.x row); which 6.x layer draws it is still open.
3. **No bomb, explosion or arrow sprites, no item-list icons.** Likely the
   art set (Seihai's default art has none of these images); not proven to
   be a client bug.
4. **No C>S 23 base-file requests and no keep-alive 24.** Already open in
   the README.
5. **46 order.** At login these servers send the props (9) before the level
   (6), so 46 goes right after the first C>S 2 props, in the same flush.
   When 6 comes first it goes before the props. Which order the original
   uses at login is not known.

## Server findings (for seihai)

- The GServer-v2 fork never sends 108 and never relays the bomb (11); the
  Rust server does both.
- Rust `import-v2` keeps a version range (`modern = G3D11125:G3D0511C`)
  that the server then ignores, locking out `G3D0511C` until
  `allowedversions.txt` is edited.
- `import-v2` drops weapons and account WEAPON lines.
- On the Rust server the AP bar is empty; the fork shows AP 50.
